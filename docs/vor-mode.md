# 前庭固视模式 (VOR Mode)

`data-mode="vor"` — 在「🎯 射击模式 - 消灭敌舰」基础上派生的前庭眼反射 (VOR) 训练模式。

## 训练原理

| | 射击模式 (shooting) | 前庭固视模式 (vor) |
|---|---|---|
| 飞船 | 随头动左右移动 | **固定在屏幕底部中央**（固视靶） |
| 画面 | 静止（仅星野滚动） | **随头部 yaw 反向平移** |
| 视线 | 跟着飞船跑 | **锁定不动的飞船** |
| 训练目标 | 颈椎 ROM / 追踪 | **头动中的凝视稳定（VOR 增益）** |

头向右转 → 画面向左移；头向左转 → 画面向右移。患者视线始终锁定屏幕底部中央那台不动的飞船，
头在动而视线不离靶 —— 这正是 VOR 训练要的东西。

## 运动学参数

```
水平量程     ±20°   （window.__vorRangeDeg 可覆盖）
画面最大位移  ±0.32 屏宽 （window.__vorShiftMax 可覆盖）
跟随平滑     lerp 0.5/帧 —— 刻意远高于射击模式的 0.45 惯性感，
                          VOR 必须跟手，滞后会破坏凝视稳定
垂直轴       不启用（pitch/roll 忽略），单轴训练降低眩晕风险
飞船纵向位置  playerY = 0.88（射击模式为 0.95，上移以便固视靶完整可见）
```

超过 ±20° 的输入被钳制（画面不再继续移动），但原始角度仍被记录用于反馈。

## 实现要点

核心技巧 —— **不平移实体，而是平移参考系**：

```
worldShift        = -clamp(yaw / 20, ±1) * 0.32
player.x (世界坐标) = 0.5 - worldShift
渲染时             世界层 ctx.translate(worldShift * w, 0)，飞船画在固定的 0.5
```

因此所有既有的碰撞检测、锁定瞄准、子弹生成逻辑**完全不需要修改** —— 它们照旧在世界坐标里工作。

### 三层渲染，各自运动语义不同

| 层 | 内容 | 是否随头动平移 | 理由 |
|---|---|---|---|
| 固定层 | 深空渐变底色 | ✗ | 无特征，平移会在画面边缘留下可见接缝 |
| 固定层 | 太阳 / 木星 / 地球 | ✗ | 远景天体跟着晃会显得"整块画面在滑"，固定住画面更稳定好看 |
| 世界层 | 星野 / 星云 / 光带 | ✓ | 提供 VOR 需要的视觉运动线索 |
| 世界层 | 金币等障碍物 | ✓ | **碰撞判定用世界坐标，绘制必须同样平移** |
| 世界层 | 敌舰 / 子弹 | ✓ | 同上 |
| 屏幕层 | 飞船 + 固视靶 + HUD | ✗ | 固视靶必须钉死在屏幕上 |

> 踩过的坑：金币最初漏了平移（它在 `this.obstacles` 里，由 `render()` 的障碍物循环单独绘制），
> 导致画出来的位置与碰撞位置最大差 0.32 屏宽 —— 看得见却吃不到。

### 生成坐标系：跟随视野，而非固定世界坐标

这是 VOR 模式最关键的一处改动。原引擎里敌舰/金币生成在**固定世界坐标** `x ∈ 0.2~0.8`，
而 VOR 的可见视野是随头动平移的 `[-shift, 1-shift]` —— 两者脱钩会同时引发两个故障：

- 头转满 20°（shift = −0.32）时，世界 x=0.2 的敌舰落在**屏幕 −0.12，完全在画面外生成**，
  患者看不见就撞上去
- 飞船世界可达区间是 `[0.18, 0.82]`，与敌舰走廊 `[0.2, 0.8]` 几乎重合，头转到边缘时
  飞船在走廊外侧，`|敌舰.x − 飞船.x|` 永远大于锁定阈值 → **打不出子弹**

因为飞船永远在屏幕正中央，「可见」与「可达」可以用同一个公式同时满足：

```
worldX = clamp( player.x + (rand − 0.5) × 0.7 , 0.5 − shiftMax , 0.5 + shiftMax )
                └────── 可见：屏幕 0.15~0.85 ──────┘  └──── 可达：飞船世界可达区间 ────┘
```

生成瞬间必在画面内、必在可击中范围内。

**左右交替生成（逼患者左右转头）**：VOR 训练的核心是「左右转头盯住飞船标靶」，纯随机生成
可能连续几十秒全在同一侧。改为**敌舰、金币各自独立批次**，每侧连续 2 个后切换：

- 左：世界 x ∈ [lo, player.x − 0.04]（屏幕左半）
- 右：世界 x ∈ [player.x + 0.04, hi]（屏幕右半）
- 贴边时（本侧已无空间，如头转满 20°）本次强制对侧 —— 物理必然，且驱动患者回中线
- 状态挂在 engine 实例上（`_vorSpawnSide`/`_vorBatch`），**不用类字段语法** ——
  类字段在这种压缩类体里不可靠（踩过坑，字段声明未生效）

此外 fighter 类敌舰原有 `speedX ±0.015/s` 横向漂移，
生成在可达边界后会漂出飞船够不到的范围（永远打不掉），VOR 下一并锁死为 0 ——
转头去追横移目标不是前庭训练要的动作，头动应当由「敌舰生成在哪」驱动。

### 生成节奏放慢（VOR 专属）

用户反馈"敌舰生成太快来不及射击"：实测同时在场峰值可达 **7 个**，每个需 0.5s 锁定，
打 3 个的功夫其他 4 个已到飞船。VOR 是前庭训练不是反应测试，三项放慢（仅 VOR）：

| 参数 | 射击模式 | VOR 模式 | 效果 |
|---|---|---|---|
| 生成间隔 | 1s | **2s** | 生成率减半 |
| 敌舰在场上限 | 随难度增长 | **3 个** | 不堆积 |
| 下落速度 | 0.12~0.24/s | **×0.6 (0.07~0.14/s)** | 穿越时间 4~8s → **10~12s** |

实测：在场峰值 7 → **3**，玩家有充足时间逐个转头锁定击毁。

### 开火纪律：必须真正对准才射击

原设计的规则是「对准并保持住才开火」，VOR 完整沿用，**不放宽**：

| 参数 | 值 | 说明 |
|---|---|---|
| `alignmentThreshold` | 0.02（屏幕约 18px） | 与射击模式一致 |
| `requiredHoldTime` | 0.5 s | 与射击模式一致 |
| 开火后 | `alignmentTime = 0` | 每次齐射都要重新对准 |
| 实测齐射频率 | **约 0.8 次/秒** | 不是连发 |

但原引擎的锁定逻辑有个**漏洞**，在 VOR 下会破坏这条规则：

```js
this.targetEnemy = n,                        // 每帧无条件切到最近敌舰
n && r < alignmentThreshold ? alignmentTime += dt
                            : alignmentTime -= dt*2   // 只衰减，不清零
canShoot(){ return targetEnemy && alignmentTime >= requiredHoldTime && ... }
```

对准敌舰 A 攒满 0.5 s 后，A 被击毁或移出候选范围，目标瞬间切到远处的 B，
而 `alignmentTime` 还要 0.25 s 才排空 → **朝根本没对准的 B 开火**。
实测偏差可达 0.0695，是阈值的 3.5 倍。VOR 下目标切换更频繁，所以特别明显。

两处修补让规则在开火那一刻硬性成立：

1. **目标切换时 `alignmentTime` 立即清零** —— 蓄力不能跨目标继承
2. **`canShoot()` 增加"当前这一帧确实对准"的硬校验** —— 不依赖历史累积值

修补后实测最大偏差 **0.0695 → 0.0073**（4 轮采样，均 < 0.02）。

> 这个漏洞在射击模式里同样存在，但为避免影响已上线模式，补丁只在 VOR 下生效。

### 视野外敌舰的边缘箭头

即使生成时可见，患者转头仍可能把已有敌舰推出画面。屏幕边缘会在对应高度画**琥珀色三角箭头**，
透明度随离屏距离衰减，避免"看不见→误判→被撞"。

### 锁定的可视化反馈

「必须对准才射击」要可执行，患者就得看得见该把敌舰推到哪：

- **锁定进度环**：画在目标敌舰的屏幕位置上，青色圆弧表示蓄力进度，
  环满转绿并出现实心点 → 此时才会开火

不画从飞船指向上方的射击引导线：那样的竖线会把视线往上牵引，
而 VOR 训练要求视线钉死在飞船上不动，引导线与训练目标直接冲突。

（场景自带的 `aimIndicator` 在 VOR 下关闭 —— 它绘制在 `translate(飞船屏幕坐标)` 的上下文里
却用绝对坐标，VOR 下会错位，改由引擎在正确的坐标系重画。）

### 锁定候选的 y 上界

原筛选 `e.y < 0.8`，而 VOR 下飞船在 `y = 0.88` —— 敌舰从 0.8 到 0.88 这最后一段
**无法被锁定**，表现就是"明明对准了却打不出子弹"。VOR 下放宽到 `playerY − 0.02`。
这是修错配，不是放宽标准。

### VOR 专属金币调参

原参数在 VOR 下太难吃（实测机器人级完美追踪也只有 **42%** 收集率），四个原因：

1. `speedY 0.28~0.48` → 从生成到飞船只有 2~3.5 秒对准窗口
2. 生成 `x 0.2~0.8` → 边缘金币要打满 ±20° 才够，零余量
3. `speedX ±0.015` → 追踪时目标自己还在横向跑
4. 命中判定半径按 `min(w,h)` 缩放而位置按 `width` 缩放 → 横屏下横向容差只有纵向的 1/1.65

VOR 是前庭训练，金币是奖励物而非反应速度考核，故放宽（**仅 VOR 模式**，射击模式参数不变）：

| 参数 | 射击模式 | VOR 模式 |
|---|---|---|
| 生成 x | 0.2 ~ 0.8 | **`_vorSpawnX()`**（跟随视野，见上节） |
| 下落速度 | 0.28 ~ 0.48 | **0.16 ~ 0.26** |
| 横向漂移 | ±0.015 | **0** |
| 半径 | 0.025 | **0.04** |
| 上下浮动 | 0.03 | **0.012** |

收集率：**42% → 86%**（生成改为跟随视野后进一步到 100%）

## HUD 反馈

- **固视靶环**：飞船周围虚线圆 + 四角刻线，提示患者视线锁定位置
- **顶部角度条**：实时头位，中线为 0°
  - 青色 = 未到位
  - **绿色 = 到位**（≥95% 量程，即训练目标达成）
  - 琥珀色 + "超范围" = 超出量程 25% 以上
- **训练计数**：转头（方向反转）次数 · 峰值角度

## 采集指标

`engine.getVorStats()` / `engine._vorStats`：

| 字段 | 含义 |
|---|---|
| `maxDeg` | 本次训练峰值转头角度 |
| `turns` | 有效转头次数（方向反转，阈值 35% 量程） |
| `outOfRangeSec` | 处于量程边界（钳制状态）的累计秒数 |

## 代码落地方式

游戏源码（`js/game/*.js`）仅存在于 `git stash@{0}`，当前分支只有构建产物，
因此本模式以**断言式补丁**方式落在构建产物上：

```bash
npm run patch:vor        # 幂等；每个锚点校验唯一性，任一不匹配则整体中止不改动
```

- 目标文件：`assets/index-Cc2Ik-Ku.js`（index.html 唯一加载的主包）
- 备份：`tools/index-Cc2Ik-Ku.js.bak-vor`（不在 assets/ 下，不会被部署）
- 标记：`/*VOR-PATCH-v13*/`（存在则跳过）
- `assets/index-C_dSa6Qp.js` 无任何 HTML 引用，是死产物，未改动

## 验证

```bash
npx vite --port 4399           # 起本地服务
npm run test:e2e:vor           # VOR 模式 15 项断言
npm run test:e2e:vor-coins     # 金币收集率 + 星球固定 6 项断言
npm run test:e2e:vor-vis       # 生成可见性 + 左右交替 + 节奏 + 边缘箭头 13 项断言
npm run test:e2e:vor-fire      # 开火纪律(必须对准才射击) 8 项断言
npm run test:e2e:shooting      # 原射击模式 9 项回归
```

E2E 用 `window.updateFromGyroscope()` 注入陀螺仪数据，并通过反解 yaw 追踪最近敌舰
做**确定性**瞄准测试（不依赖随机摆头恰好命中）。

> **测试环境坑**：必须用纯静态服务器（`python -m http.server`）跑 E2E。
> vite dev server 在 Windows 上会漏掉对 `assets/` 文件的变更监听，返回缓存的旧版本 ——
> 曾导致"产物有箭头代码但浏览器里函数没有"的假 bug，排查了十几轮才发现是缓存。

开火纪律的证明方式：钩住 `scene.playerShoot`，在**每次真实发射的瞬间**记录 `|敌舰.x − 飞船.x|`，
断言其恒小于 `alignmentThreshold`；同时用引擎自己的 `gameTime` 作时基统计齐射间隔
（用 `performance.now()` 会与引擎 `deltaTime` 产生漂移，导致 0.5 s 误测成 0.494 s）。

截图：`screenshots/vor-mode-{center,target20,over-range}.png`、`screenshots/vor-v3-{center,left20,right20}.png`、
`screenshots/vor-lockon.png`（锁定进度环）

星球固定的验证方式：采样太阳所在区域（0.88w, 0.12h）的像素亮度，比较 yaw=0 / +20° / −20° 三种
头位下是否一致（实测 Δ=0）。
